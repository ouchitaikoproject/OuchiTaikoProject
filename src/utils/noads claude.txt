Why the Current Code Causes This
Every single frame (hundreds of times per second), the firmware reads all 4 ADC channels. Even when you're not hitting anything, those channels return small noisy values — maybe 5, 12, 30, whatever. Pure electrical noise.
The current code does this before checking if anything is actually above threshold:

"Which is bigger right now — the total Don signal or the total Ka signal?"

Since it's just noise, Don might be slightly bigger than Ka this frame. So the code zeros out the entire Ka zone. Next frame, Ka noise is slightly bigger, so Don gets zeroed. This flip-flops randomly at full loop speed.
Now here's the part that actually hurts you: when it zeros the losing zone, it doesn't just ignore it — it calls setState(false, 0) on those pads, which bypasses debounce entirely (the 0 means "no wait, go inactive right now"). So even if Ka just legitimately triggered and is supposed to stay active for 12ms (your debounce window), if Don noise wins the next frame's coin flip, Ka gets force-killed instantly.
The result: hits register for maybe 1-2 frames and then get violently cancelled before the USB report even gets sent. In a gamepad tester this looks like nothing happening, or a very brief flash of a button that immediately releases.
The noise floor guard (if raw_max_don >= noise_floor || raw_max_ka >= noise_floor) was supposed to prevent this — "only arbitrate when there's a real signal." So the guard fires more often than intended, and you're still in the flip-flop situation during the rising and falling edge of every real hit.
